# MASTER PROMPT: COMPLETE GROCERY SHOP PRICE MANAGEMENT WEBSITE

## 1. Role and Objective

Act as a senior full-stack web developer, software architect, database engineer, UI/UX designer, and software tester.

Build a complete, professional, responsive, and fully functional **Grocery Shop Price Management Dashboard** for managing grocery products, categories, brands, quantities, selling prices, price-change history, and voice-based product search.

The application must be a real working website, not just a design, static HTML page, or frontend prototype.

The shop owner must be able to add products, edit prices, create categories, search for products using text or voice, and see updated prices immediately across the entire website.

**Critical requirement:** Each product must have one authoritative record in the database. Whenever a product price is changed and saved, every page that displays that product must show the latest price automatically.

Build the complete application inside the currently opened project workspace.

Do not stop after generating a plan or creating the homepage. Implement the entire application, run it, test it, fix errors, and provide instructions for using it.

## 2. Recommended Technology Stack

Use the following technology stack unless the existing project requires a compatible alternative.

- Frontend: React with TypeScript.
- Build tool: Vite.
- Styling: Tailwind CSS.
- Icons: Lucide React.
- Database: Supabase with PostgreSQL.
- Routing: React Router.
- Form validation: Zod or an equivalent validation library.
- Date formatting: A reliable date-formatting library or native date APIs.
- Voice search: Web Speech API where supported.
- State management: React Context, Zustand, or another appropriate solution.
- Notifications: Toast messages for successful operations and errors.

Use a modular, maintainable architecture with reusable components.

Do not introduce unnecessary dependencies or overly complicated infrastructure.

If Supabase credentials are unavailable, implement a clearly separated local development mode using browser storage or IndexedDB so that the website can still be tested. Clearly explain that local development storage does not provide automatic synchronization across devices.

Never expose secret credentials in frontend source code.

## 8. Voice-Based Grocery Search

Implement an actual voice-search feature using the device microphone and speech recognition.

Display a microphone button beside the search field.

### Voice-search workflow

1. The user clicks the microphone button.
2. The website requests microphone permission when required.
3. The application listens for the user's speech.
4. The recognized speech appears as text in the search field.
5. The application identifies relevant product names, categories, brands, and quantities.
6. Search the real stored product data.
7. Display matching products and their current prices.
8. Allow the user to stop listening or clear the search.

Provide clear visual states:
- Ready to listen.
- Listening.
- Recognized text.
- Searching.
- Results found.
- No results.
- Permission denied or unsupported browser.

### Example English voice commands

- "Show Ponni Rice."
- "Find five kilogram Ponni Rice."
- "Show sunflower oil one litre."
- "Search Lux soap."
- "Show wheat flour."
- "Show all rice products."
- "Find coconut oil."
- "Show products in the soap category."

### Tamil and Tamil-English mixed speech

Support English and Tamil where the browser or selected speech-recognition engine supports them.

Examples:
- "Ponni rice kaattunga."
- "Rice price sollunga."
- "Five kilo Ponni rice kaattu."
- "Coconut oil irukka?"
- "Soap category kaattu."

Provide an appropriate speech-recognition language selection, such as English (India) and Tamil (India), when supported.

For mixed-language input, normalize recognized words and implement practical matching against product names, brand names, categories, and quantities.

Do not promise perfect recognition for every accent or mixed-language phrase. Browser and device support may vary.

### Search behavior

For example, if the database contains:

- Ponni Rice, Brand A, 1 kg, ₹65.
- Ponni Rice, Brand A, 5 kg, ₹320.
- Ponni Rice, Brand B, 1 kg, ₹68.
- Ponni Rice, Brand C, 10 kg, ₹620.

When the user says "Show Ponni Rice," display all four matching products.

When the user says "Ponni Rice five kilogram," prioritize the matching 5 kg product.

If the user requests a category, show its relevant products.

If no match is found, suggest similar product names or categories.

### Fallback behavior

If speech recognition is unsupported, unavailable, or permission is denied:
- Keep text search fully functional.
- Display an informative message.
- Do not crash the website.
- Do not display fake voice-search results.

Voice search must use the same current product data as the rest of the website.

## 9. Price Change History

Create a Price History page that records all successful product price changes.

For every actual price change, store:

- History ID.
- Product ID.
- Product name at the time of the change.
- Brand.
- Package quantity.
- Previous price.
- New price.
- Price difference.
- Change date and time.
- User who made the change, if authentication is enabled.

Example:

| Product | Previous Price | New Price | Difference |
|---|---:|---:|---:|
| Ponni Rice, 1 kg | ₹60 | ₹65 | +₹5 |
| Sunflower Oil, 1 L | ₹145 | ₹150 | +₹5 |
| Wheat Flour, 1 kg | ₹55 | ₹52 | -₹3 |

These values are illustrative.

### Price history requirements

- Record history only after a successful price update.
- Do not create a price-change record when the price has not changed.
- Preserve historical records if a product is renamed or deleted.
- Display the actual change date and time.
- Sort history from newest to oldest by default.
- Allow filtering by product, category, and date range.
- Show previous and current prices clearly.
- Calculate price differences correctly.
- Prevent ordinary users from editing historical records.

Use the database or server-generated timestamp as the authoritative time when a change is saved.

Store timestamps consistently and display them in the appropriate local time zone, normally Asia/Kolkata for this application.

The product's Last Price Changed field must only update when its price actually changes, not when an unrelated field such as its description is edited.

Where supported, save the product update and price-history entry in one database transaction so that the two records cannot become inconsistent.

## 11. Database Design

Create a reliable database schema using PostgreSQL through Supabase.

### Table A: categories

Fields:
- id: UUID primary key.
- name: Text, required.
- display_order: Integer.
- created_at: Timestamp.
- updated_at: Timestamp.

### Table B: products

Fields:
- id: UUID primary key.
- category_id: UUID foreign key referencing categories.
- name: Text, required.
- brand: Text.
- quantity_value: Numeric, required.
- quantity_unit: Text, required.
- price: Numeric, required.
- sku: Optional text.
- description: Optional text.
- created_at: Timestamp.
- updated_at: Timestamp.
- last_price_changed_at: Timestamp.

### Table C: price_history

Fields:
- id: UUID primary key.
- product_id: UUID, nullable when necessary to preserve history after deletion.
- product_name_snapshot: Text.
- brand_snapshot: Text.
- quantity_snapshot: Text.
- previous_price: Numeric.
- new_price: Numeric.
- price_difference: Numeric.
- changed_at: Timestamp.
- changed_by: Optional user ID.

Use appropriate foreign-key rules, indexes, constraints, and numeric types for currency values.

Use a suitable transaction or database function to ensure the product price and its history entry remain consistent.

The price-history record must contain enough snapshot information to remain understandable even if the product is later renamed or deleted.

### Data consistency

- Use stable product IDs.
- Store the current price in the products table.
- Store historical changes in the price_history table.
- Never calculate the current price from an arbitrary historical record.
- Never hardcode real product prices in UI components.
- Use one reusable data-access layer for all pages.
- Use database constraints and server-side validation where appropriate.

### Database deliverables

Generate:
- SQL schema and migration files.
- Required indexes and constraints.
- Appropriate database functions or triggers if needed.
- Seed data for optional demonstrations.
- Clear database setup instructions.

Make sure the schema is reproducible on a fresh Supabase project.

## 12. Data Persistence and Multi-Device Synchronization

All actual product and category information must be saved persistently.

The website must not lose saved data when:
- The browser is refreshed.
- The application is restarted.
- The user signs out and back in.
- The user opens the website from another supported device.

Use Supabase as the shared database when configured.

If multiple devices are supported, updates made on one device must become visible on the others without manually re-entering the information.

Implement real-time subscriptions where appropriate, or use reliable query refresh and cache invalidation.

Handle network interruptions and database errors gracefully.

Do not display an update as saved when it has not been successfully persisted.

If offline mode is implemented, distinguish unsaved or locally cached changes from confirmed database changes. Provide an appropriate synchronization strategy rather than silently overwriting newer data.
